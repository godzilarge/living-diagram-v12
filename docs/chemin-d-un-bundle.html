Le chemin d'un bundle

état au 2026-10-04, soir · complément de l'artefact d'architecture

Tu envoies un JSON qui décrit une infrastructure à un instant donné. Il est validé, rangé, et depuis le 2026-09-20 B1 sait le transformer en graphe : des nœuds (les équipements) et des câbles, déduits en croisant LLDP, CDP et les descriptions, chacun avec ses preuves. Ce graphe est maintenant rangé à côté du bundle à chaque ingestion et servi par l'API. Et tu peux maintenant le voir : ld render bundle.json --out page.html écrit une page HTML autonome, hors ligne, qui montre le graphe et, pour chaque câble, les sources qui l'ont tracé. Depuis le 2026-09-26, B1 reconstruit aussi les agrégats, les domaines vPC / MLAG et les clusters HA, la page les dessine (bandes sous les câbles, cadre autour des membres d'un cluster, onglet Structures), et le backend la sert (/view, jeton saisi dans la page). Depuis le 2026-10-03, ld-contracts generate fabrique des infrastructures synthétiques entières, sur plusieurs runs avec des pannes nommées, pour essayer tout cela sans attendre un bundle réel. Depuis le 2026-10-04, le diff entre deux runs (B3) est écrit : ld diff, GET /api/diff, et la page peint ce qui a changé (ld render --from, /view?…&from=). Le soir du même jour, ton cap est tenu : la page est devenue la toile (engine/, TypeScript, mêmes rendus à l'octet) et l'intention existe : dans /view, avec ton nom, glisser un équipement l'épingle pour tout le monde, l'épingle survit aux runs, l'onglet Intentions dit qui a épinglé quoi. Le pas à pas est dans QUICKSTART.md, à la racine du dépôt.

Le chemin, étape par étape

Dans l'ordre où un bundle les traverse. Les trois premières étapes sont celles que tu as en tête ; les suivantes sont la raison d'être de l'application.

Une run de collecte, une infrastructure : devices, tasks, interfaces, agrégats, lldp, cdp, system, ha. Le format est le contrat d'entrée, RunBundle v1.

Le contrat d'entrée le vérifie

Le bundle brut est archivé
Un dossier par (infrastructure, run) : le JSON tel que reçu, son empreinte, le rapport d'ingestion. Immuable : renvoyer le même bundle répond 200, un bundle différent pour la même run répond 409.

5
B1 transforme le bundle en graphe : le snapshot
Résout les voisins cités par LLDP, CDP et les descriptions ; fusionne les témoignages en câbles (confirmé, observé seul, documenté seul) ; reconstruit agrégats, vPC, clusters HA ; émet les contrôles (désaccord description / LLDP, membre suspendu, device injoignable…). Fonction pure : même bundle, même snapshot, à l'octet.

6
Le contrat de sortie vérifie le snapshot
La forme exacte du graphe (nœuds, interfaces, liens avec leurs preuves, agrégats, domaines MLAG, clusters, contrôles, couverture, rapport). Plus strict que le contrat d'entrée : un snapshot incohérent est refusé, pas signalé, parce qu'un snapshot faux est un bug de B1, pas de la donnée. Il fixe aussi l'ordre des listes, donc les octets.
contracts/src/ld_contracts/snapshot/ · CONTRAT.md partie B · ld-contracts validate --contract snapshot
réalisé
7
Le snapshot est archivé à côté du bundle, l'API le sert
snapshot.json dans le même dossier que le bundle, lu par GET /api/snapshot?infrastructure=&run_id=. Si B1 échoue, l'ingestion réussit quand même : le bundle est archivé, la réponse dit correlation: failed. Le snapshot est le seul fichier remplaçable de l'archive : ld correlate le recalcule depuis le bundle, sans la base amont, quand une règle de B1 a été corrigée.
backend/src/ld_backend/snapshots.py · ingest.py après archive.store · cli.py (ld correlate)
réalisé
8
Une page HTML montre le snapshot : ld render
Voir avant de trancher (décision du 2026-09-20). Un seul fichier HTML, sans librairie ni réseau, ouvrable par double-clic. ld render bundle.json --out page.html valide, corrèle et dessine sans archive ni serveur : c'est ta boucle de mise au point d'exportateur. Quatre vues : le graphe (câbles verts confirmés, bleus observés seuls, orange pointillés documentés seuls ; cliquer un câble montre les sources qui l'ont tracé : qui témoigne, ce qu'il annonce, comment le nom a été résolu), les contrôles, la qualité des données (couverture par équipement et par topic, constats d'ingestion, descriptions non lues, voisins non résolus) et les sources (câbles par combinaison LLDP / CDP / description). La page contient tes données : elle ne sort pas de la zone sans anonymisation du bundle. Incrément B (2026-09-26) : une bande par faisceau d'agrégat sous ses câbles (étiquetée peer-link ou MLAG), un cadre par cluster HA autour de ses membres, un halo sur un câble de heartbeat, un onglet Structures ; cliquer une bande ou un cadre montre l'agrégat, le faisceau ou le cluster avec ses membres, ses câbles et ses sources (le document aggregates ou ha de chaque équipement). Et la page est servie par le backend : /view?infrastructure=&run_id=, sans jeton dans l'adresse, le jeton se saisit dans la page et reste dans l'onglet.
backend/src/ld_backend/render/ · mode d'emploi : QUICKSTART.md · un premier bundle réel : devices, tasks, interfaces, lldp, cdp suffisent ; aggregates et ha en plus pour voir les structures
incréments A et B réalisés
9
La toile le dessine, et tu y poses tes intentions
Fait le 2026-10-04 : la page de l'étape 8 est devenue le moteur, engine/ en TypeScript (portée telle quelle : mêmes rendus à l'octet, même page servie sur /view). Le diff entre deux runs (B3) s'y lit (ld render --from, /view?…&from=). La couche d'intention (B4) y est : dans /view, tu donnes ton nom, tu glisses un équipement, il est épinglé pour tout le monde (API POST /api/intent/patches, journalisé), et il reste à sa place aux runs suivantes ; l'onglet Intentions liste les épingles, dit celles dont l'équipement a disparu (orphelines, jamais effacées en silence), et les retire. Ce qui reste du moteur : le placement seedé par la run d'avant (pour que tout tienne en place, pas seulement les épingles), les autres intentions (masquer, annoter), les niveaux de détail.

Pourquoi le formulaire de sortie avant la machine

Trois raisons, dans l'ordre où elles comptent.

1. B1 s'écrit en TDD contre ce contrat : chaque test dit « le snapshot produit est valide et égal, à l'octet, au snapshot attendu ». Sans contrat, pas de « attendu ».
2. Le contrat porte les invariants qu'on ne veut jamais renégocier : pas de câble inventé, pas d'identifiant synthétique, listes triées, toute référence résolue. B1 ne peut pas les violer par accident, le type les refuse.
3. C'est la frontière avec le front : les types TypeScript du moteur seront générés depuis ce schéma, pas écrits à la main.
Le diff B3, la toile et les épingles sont écrits (2026-10-04) : ld diff, GET /api/diff, engine/, GET /api/intent, POST /api/intent/patches, glisser-déposer enregistré dans /view. Prochaine étape : tes retours sur le front. La table MAC (docs/06) est conçue et parquée.
