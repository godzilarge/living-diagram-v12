Le chemin d'un bundle

état au 2026-09-22 · complément de l'artefact d'architecture

Tu envoies un JSON qui décrit une infrastructure à un instant donné. Il est validé, rangé, et depuis le 2026-09-20 B1 sait le transformer en graphe : des nœuds (les équipements) et des câbles, déduits en croisant LLDP, CDP et les descriptions, chacun avec ses preuves. Ce graphe est maintenant rangé à côté du bundle à chaque ingestion et servi par l'API. Et tu peux maintenant le voir : ld render bundle.json --out page.html écrit une page HTML autonome, hors ligne, qui montre le graphe et, pour chaque câble, les sources qui l'ont tracé. La suite : ton premier bundle réel, puis les agrégats et les clusters de firewalls. Le pas à pas est dans QUICKSTART.md, à la racine du dépôt.

Le chemin, étape par étape

Dans l'ordre où un bundle les traverse. Les trois premières étapes sont celles que tu as en tête ; les suivantes sont la raison d'être de l'application.

1
Ton exportateur produit bundle.json
Une run de collecte, une infrastructure : devices, tasks, interfaces, agrégats, lldp, cdp, system, ha. Le format est le contrat d'entrée, RunBundle v1.
chez toi, zone sécurisée · référence : contracts/CONTRAT.md partie A

2
Tu l'envoies : POST /api/ingest/bundles
Ou en ligne de commande, ld ingest bundle.json, même code. Jeton Bearer obligatoire.
backend/src/ld_backend/api.py · cli.py
réalisé
3
Le contrat d'entrée le vérifie
Types stricts, identités uniques, périmètre de l'infrastructure. Refus (422) si le format n'est pas respecté ; constats non bloquants sinon (clé oubliée, membre d'agrégat inconnu…).
contracts/src/ld_contracts/ (bundle.py, checks.py, defaults.py) · appelé par ingest.py
réalisé
4
Le bundle brut est archivé
Un dossier par (infrastructure, run) : le JSON tel que reçu, son empreinte, le rapport d'ingestion. Immuable : renvoyer le même bundle répond 200, un bundle différent pour la même run répond 409.
backend/archive/<infra>/<run>/ · archive.py (début de B2)
réalisé
5
B1 transforme le bundle en graphe : le snapshot
Résout les voisins cités par LLDP, CDP et les descriptions ; fusionne les témoignages en câbles (confirmé, observé seul, documenté seul) ; reconstruit agrégats, vPC, clusters HA ; émet les contrôles (désaccord description / LLDP, membre suspendu, device injoignable…). Fonction pure : même bundle, même snapshot, à l'octet.
backend/src/ld_backend/correlate/ · règles R0 à R3 et R6 de docs/05 · revue et contre-revue dans docs/revues/ · agrégats, vPC, HA et contrôles d'état : étape 2
en cours · 2 étapes sur 3
6
Le contrat de sortie vérifie le snapshot
La forme exacte du graphe (nœuds, interfaces, liens avec leurs preuves, agrégats, domaines MLAG, clusters, contrôles, couverture, rapport). Plus strict que le contrat d'entrée : un snapshot incohérent est refusé, pas signalé, parce qu'un snapshot faux est un bug de B1, pas de la donnée. Il fixe aussi l'ordre des listes, donc les octets.
contracts/src/ld_contracts/snapshot/ · CONTRAT.md partie B · ld-contracts validate --contract snapshot
réalisé
7
Le snapshot est archivé à côté du bundle, l'API le sert
snapshot.json dans le même dossier que le bundle, lu par GET /api/snapshot?infrastructure=&run_id=. Si B1 échoue, l'ingestion réussit quand même : le bundle est archivé, la réponse dit correlation: failed. Le snapshot est le seul fichier remplaçable de l'archive : ld correlate le recalcule depuis le bundle, sans la base amont, quand une règle de B1 a été corrigée.
backend/src/ld_backend/snapshots.py · ingest.py après archive.store · cli.py (ld correlate)
réalisé
8
Une page HTML montre le snapshot : ld render
Voir avant de trancher (décision du 2026-09-20). Un seul fichier HTML, sans librairie ni réseau, ouvrable par double-clic. ld render bundle.json --out page.html valide, corrèle et dessine sans archive ni serveur : c'est ta boucle de mise au point d'exportateur. Quatre vues : le graphe (câbles verts confirmés, bleus observés seuls, orange pointillés documentés seuls ; cliquer un câble montre les sources qui l'ont tracé : qui témoigne, ce qu'il annonce, comment le nom a été résolu), les contrôles, la qualité des données (couverture par équipement et par topic, constats d'ingestion, descriptions non lues, voisins non résolus) et les sources (câbles par combinaison LLDP / CDP / description). La page contient tes données : elle ne sort pas de la zone sans anonymisation du bundle. Reste : la servir depuis le backend, puis y montrer agrégats et clusters HA.

Pourquoi le formulaire de sortie avant la machine

Trois raisons, dans l'ordre où elles comptent.

1. B1 s'écrit en TDD contre ce contrat : chaque test dit « le snapshot produit est valide et égal, à l'octet, au snapshot attendu ». Sans contrat, pas de « attendu ».
2. Le contrat porte les invariants qu'on ne veut jamais renégocier : pas de câble inventé, pas d'identifiant synthétique, listes triées, toute référence résolue. B1 ne peut pas les violer par accident, le type les refuse.
3. C'est la frontière avec le front : les types TypeScript du moteur seront générés depuis ce schéma, pas écrits à la main.
Prochaine étape : la tranche visible — brancher B1 (étape 7), puis les pages HTML de visualisation avec les sources de chaque élément (étape 8), à essayer sur un premier bundle réel. Ensuite seulement : B1 étape 2, table MAC, moteur.
