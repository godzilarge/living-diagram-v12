## Constats

### H1 (haut) — Une annotation attachée, sélectionnée avec son ancre, bouge deux fois (flèches, aligner, mettre en grille)

**Où** : `engine/src/app/canvas/toile.ts:347` (`movableNotes`), `:358` (`shiftNote`), `:385-398` (`alignSelected`,
chemin par les boîtes), `:425-430` (`gridSelected`), `:454-460` (`nudge`).

**Scénario** :
1. On sélectionne une carte et la note attachée à elle. Le cas le plus courant est **Ctrl+A puis une flèche**, qui prend
   toutes les cartes et toutes les notes.
2. La toile déplace la carte (épingle) **et** ajoute le même écart à `x / y` de la note.
3. Or `x / y` d'une note attachée est son écart **à son ancre** (A0). La note bouge donc de deux fois l'écart.
4. Le résultat est écrit dans l'intention partagée, sous le nom de l'auteur.

Le même défaut touche une note ancrée à un **groupe** dont le cadre est sélectionné : `movable()` y ajoute les membres,
le cadre bouge, et la note avec.

**Vérifié** :
- Chromium (S4) : une flèche donne carte `dx = 20` et note `dx = 40` ; l'écart enregistré passe de 60 à 80.
- Node (sonde `sonde-align-attached.cjs`) : « aligner à gauche » pose la note à `x = -500` au lieu de `-100` ; la grille
  la pose de même hors de sa case.
- Le glissé à la souris n'est **pas** touché : React Flow exclut un enfant dont le parent est sélectionné.

**Correction proposée** : dans les trois gestes, ne pas décaler l'écart d'une annotation dont l'ancre bouge dans le même
geste (ancre `device` ∈ hôtes déplacés ; ancre `group` dont le cadre suit). Pour aligner et mettre en grille, calculer la
boîte visée dans le plan, puis écrire `écart = visée − nouveau point de référence de l'ancre`.
`clip-toile.targetOf().anchorAt` sait déjà le faire. Un test Node sur `createToile` le fixerait (voir D2).

### M1 (moyen) — Flèches puis Suppr (ou Ctrl+X) en moins de 400 ms : exception non rattrapée, épingles de la rafale perdues

**Où** : `toile.ts:353` (`noteAt` lit `model.annotationById.get(id).x` sans garde) ; `:445-453` (`flush`) ;
`store.tsx:348` (`deleteSelection` n'appelle pas `toile.flush()`). Même manque dans `clipboard-commands.ts:97` (`cut`),
`store.tsx:438` / `:474` (`annotationDelete`, `connectorDelete`), la corbeille de la barre (`FloatingBar.tsx:184`).

**Scénario** :
1. Une sélection mixte (note + équipement) est poussée d'un carreau ; la rafale est ouverte pour 400 ms.
2. Suppr part tout de suite. La réponse retire la note du modèle, et le dessin suivant oublie sa boîte locale
   (`Flow.tsx:178`).
3. À 400 ms, `flush` déclenche `noteOps`, puis `noteAt`, puis un `TypeError`. `save` et `settle` ne sont pas appelés.
4. L'équipement reste déplacé à l'écran, mais **son épingle n'est jamais écrite**, sans aucun message. Aucune entrée
   d'annulation n'est créée non plus. Au rechargement, il revient à sa place.

Pour un connecteur supprimé, `endOf` rend `free(0, 0)`. La requête part avec un `connector_update` sur une identité
morte : elle reçoit un 422, et **tout** le paquet est refusé, épingles comprises.

**Vérifié** : Chromium (S1) : `Uncaught TypeError: Cannot read properties of undefined (reading 'x')`, toile `x -158 →
-138`, épingle côté serveur `None` avant comme après ; Node (`sonde-nudge-delete.cjs`) : même exception.

**Correction proposée** : `toile.flush()` en tête de `deleteSelection`, de `cut`, de `annotationDelete`, de
`connectorDelete` et de `groupDelete` (comme `undo.step` le fait déjà) ; en défense, `noteOps` et `lineOps` filtrent les
identités absentes du modèle.

### M2 (moyen) — Un geste de plus de 500 opérations fait plusieurs entrées d'annulation et n'est pas atomique

**Où** : `shell/intent.ts:108` (`send` découpe par `OPS_PER_REQUEST = 500`) ; `api/writers.ts:39` (l'observateur
d'annulation enregistre **chaque** requête).

**Scénario** : à la jauge, Ctrl+A prend 520 éléments (mesuré au lot 2). Une flèche, un alignement, « mettre en grille »
ou Suppr produit plus de 500 opérations, donc deux requêtes, donc deux entrées dans la pile. Ctrl+Z n'annule que la
seconde moitié. Si la seconde requête est refusée, la première reste écrite. Cela viole la règle du lot 0, « une entrée
par geste ». Le lot 3 refuse un collage de plus de 500 éléments ; les lots 2 et 8 ne bornent rien.

**Vérification** : par lecture des deux fichiers ; pas rejoué à 500.

**Correction proposée**, au choix : (a) l'hôte d'intention chaîne ses morceaux (`undo.chain(part[i + 1], part[0])`, le
mécanisme du lot 3 existe déjà) ; (b) refuser le geste au-delà de 500 et le dire, comme le collage.

### M3 (moyen, cohérence à faire trancher) — Ctrl tenu **avant** d'appuyer : « glisser libre » (lot 8) entre en conflit avec « ajouter à la sélection » (D1, lot 2)

**Où** : `Flow.tsx:97` (`MULTI_KEYS` contient `Control`) ; `Flow.tsx:358-375` (Ctrl suspend les repères).

**Scénario** : une carte A est sélectionnée ; pour placer B sans aimant, on tient Ctrl, puis on glisse B. React Flow
ajoute B à la sélection : **A et B partent ensemble**.

**Vérifié** : Chromium (S6), équipements déplacés `['fw-edge-02', 'sw-core-01']`. Ctrl pressé **pendant** le glissé se
comporte bien ; c'est ce que teste `test_app_guides.py` (il passe Ctrl comme modificateur de souris, que React Flow ne
lit pas).

**Options** : retirer `Control` de `MULTI_KEYS` (Maj et Cmd suffisent) ; ou documenter que Ctrl ne vaut « libre »
qu'une fois le glissé commencé. À trancher par Orhan.

### B1 (bas) — Échap pendant le redimensionnement d'une annotation : les repères et l'estompage restent affichés

**Où** : `annotation.tsx:114-120` (`release()` n'est appelé que dans `up`) ; `annotation.tsx:193` (la désélection démonte
les poignées sans finir le geste) ; `guide-drag.ts:139-148`.

**Scénario** : Échap vide la sélection, les poignées disparaissent, `resizeEnd()` n'est jamais appelé. La pastille
« libre » ou les lignes, ainsi que la classe `guiding` sur `.flow-host`, restent jusqu'au prochain geste.

**Vérifié** : Chromium (S3). Après Échap + relâche : `[pastille: True, guiding: True, data-guides: "on"]`.

**Correction proposée** : un effet de nettoyage dans `Handles` qui appelle `release()` au démontage si un geste est en
cours.

### B2 (bas) — Bloc de code sélectionné seul : Origine / Fin ne parcourent plus la barre contextuelle

**Où** : `code.tsx:171-181`. L'écouteur `keydown` est à la capture sur `window`, et sa liste d'exclusion ne contient ni
`.fbar` ni `[role=toolbar]`. `keyScroll` rend une valeur pour Origine et Fin même si le bloc ne défile pas.

**Scénario** : Alt+T donne le focus à la barre, puis Fin. Le code défile (ou rien ne se passe) et le focus reste sur le
premier bouton. La tabulation itinérante du lot 4 est cassée.

**Vérifié** : Chromium (S2).

| Sélection | Premier bouton | Après Fin | Après Origine |
|---|---|---|---|
| Note | `hue` | `delete` | `hue` |
| Bloc de code | `hue` | `hue` | `hue` |

**Correction proposée** : ajouter `.fbar, .band, [role=toolbar]` à la liste d'exclusion, et ne rien prendre quand
`!l.scrolls`. (Même constat que B1 de la revue du lot 16.)

### B3 (bas) — Rectangle de sélection jamais fini : la toile et React Flow divergent, la barre reste cachée

**Où** : `Flow.tsx:305-306` (`syncSelection` sort tant que `selecting.current` est posé) ; `Flow.tsx:323-338`.

**Scénario** : React Flow n'appelle pas `onSelectionEnd` dans deux cas : `elementsSelectable` passe à faux pendant le
geste (Maj + rectangle, puis **Maj+C**, qui arme l'outil connecteur : `Shell.tsx:67` ne refuse pas Maj) ; un
`pointercancel` (stylet, tactile). `selecting` reste alors posé, ainsi que `gate("rectangle")`. Tout clic suivant
sélectionne dans React Flow mais pas dans la toile, la fiche ne s'ouvre pas et la barre reste suspendue. L'état se
répare seulement au prochain rectangle réussi.

**Vérifié** : Chromium (S5). Après le clic : toile `selection: null`, React Flow `selected: true`, barre invisible.

**Correction proposée** : lire `store.getState().userSelectionActive` au lieu de la référence, ou remettre `selecting` à
`null` sur `pointercancel` et quand l'outil s'arme ; dans `Shell.tsx`, refuser Maj pour la touche C.

### B4 (bas) — Rafale de flèches non terminée au changement de run

**Où** : `Canvas.tsx:106` (la minuterie de `later`) ; `Canvas.tsx:116` (le nettoyage ne fait que `setHandle(null)`).

**Scénario** : on pousse un équipement, puis on passe à la run suivante (→ dans la bande) en moins de 400 ms. L'épingle
est écrite par l'ancienne toile, et la réponse réaligne l'**ancien** modèle. La nouvelle toile, construite avant, montre
l'ancienne place jusqu'au rechargement.

**Vérification** : par lecture.

**Correction proposée** : `created.flush()` dans le nettoyage de l'effet, avant `setHandle(null)`.

### B5 (bas, performance) — `data.multi` posé sur **toutes** les annotations

**Où** : `flow-build.ts:232`, `multi` vaut `sizeOf(state.multi) >= 2` pour chaque annotation.

**Effet** : passer d'un élément sélectionné à deux (ou l'inverse) change les données de toutes les annotations. `reuse`
ne les ressert plus et React Flow les redessine toutes, alors que seule une annotation sélectionnée lit ce drapeau
(poignées, défilement du code).

**Correction proposée** : `multi: selected && multi`.

### B6 (bas, interaction lot 16 × lot 3 H1) — Le brouillon d'un bloc de code survit au changement de run et d'infrastructure

**Où** : `app/code/view.ts:41` (`codeView` est un singleton du module) ; `code-draft.tsx:22` (le brouillon est remonté
dans la nouvelle toile) ; `code-commands.ts` (`codeCreate` écrit dans `handle()`, c'est-à-dire la toile **courante**).

**Scénario** : on insère ou on colle un code avec secret (brouillon ouvert), on change d'infrastructure, puis
Ctrl+Entrée. Le bloc est créé dans l'autre infrastructure, aux mêmes coordonnées du plan, qui ne veulent rien dire
là-bas. La règle « un collage appartient à sa toile » (revue du lot 3, H1) n'est pas tenue par le brouillon.

**Vérification** : par lecture.

**Correction proposée** : `codeView.setDraft(null)` au démontage de la toile, ou figer l'infrastructure dans le brouillon
et refuser l'enregistrement ailleurs.

### B7 (bas) — « Mettre en grille » nomme un bloc de code par sa sorte, pas par son titre

**Où** : `toile.ts:402-406`. `noteName` ignore `content.kind === "code"` et ne sait pas lire `c.title`.
`canvas/annotations.ts:154` (`summary`) le sait, lui.

**Effet** : dans l'aperçu, tous les blocs s'appellent « bloc de code » et l'ordre « par nom » ne les distingue pas.

**Correction proposée** : réutiliser `summary(a)` ; on retire du même coup une seconde règle de nommage.
