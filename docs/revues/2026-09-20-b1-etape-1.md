## CRITIQUE

**C1 — B1 lève une exception sur un bundle que le contrat accepte** — `claims.py:43-50` (`interface_check`), appelé `claims.py:73` et `:75` ; `merge.py:179-189` (`_link_check` avec témoin), appelé `:220-226` et `:241-248`.
Un contrôle émis depuis un document `lldp`/`cdp` référence `InterfaceRef(hostname, local_interface)`. Le contrat ne refuse pas un port local absent de `interfaces[]` : `local_interface_unknown` est un **constat**, et une collecte partielle (`interfaces` en `failed`, `lldp` en `success`) laisse zéro document d'interface pour le device. Le snapshot exige alors `reference_unknown` → `ValidationError` dans `assemble`. Reproduit (sondes A et B) : LLDP sur `Ethernet1/99` vers un stub ; interfaces de `sw-core-02` retirées avec topic `failed`. Le cas B est le scénario 9 poussé d'un cran, réaliste en production.
Correction : dans `interface_check` et `_link_check`, si `(hostname, name)` n'est pas dans `ctx.interfaces`, porter la référence sur `NodeRef(hostname)` et mettre `interface` dans `details`. Deux tests : « port local inconnu » et « topic interfaces en échec, lldp en succès ».

**C2 — `_reverse_seen` est O(n²), inexploitable à l'échelle cible** — `merge.py:200-205`, appelé `:237` pour chaque claim observé.
Pour chaque claim, parcours de tous les claims avec recalcul de `_witness_key`/`_target_key` (regex `expand_cisco`). Mesuré sur bundle synthétique (LLDP réciproque, hors validation) : 1 600 claims → `merge` 1,55 s ; 3 200 → 5,2 s ; 9 600 → 46 s. Extrapolé à 24 000 claims : ≈ 5 min, contre 1,5 s d'ingestion.
Correction : construire une fois `seen = {(c.source, witness_key, target_key)}` sur les claims observés et tester `(claim.source, target, witness) in seen`. Plus largement, calculer `witness_key`/`target_key` une fois par claim (champs de `Claim`) : `equivalent()` est aujourd'hui rappelé dans `group`, `_display_name` (×2 par endpoint), `_reverse_seen` et `build_links`.

## HAUT

**H1 — `multiple_observed_neighbors` non déterministe et `details.neighbors` faux** — `merge.py:215-227`.
`witness = witness_claims[0]` prend le premier claim inséré dans le groupe de la paire, qui contient les claims des **deux** sens. Sonde E (A/p voit B/q et C/r, B/q voit A/p) : permuter trois documents LLDP change la référence témoin de `(sw-core-01, Ethernet1/5)` à `(sw-core-02, Ethernet1/4)` → `canonical_json` différent. Viole la règle « même bundle ⇒ même snapshot » ; `test_permuting_every_section` ne le voit pas car la fixture n'a pas de hub. De plus `neighbors` liste les endpoints de la paire (le témoin lui-même y figure comme « voisin ») et non les voisins observés sur le port : dans le test « deux voisins » chaque contrôle porte un seul voisin (sonde F).
Correction : dans `group()`, quand `len(observed) > 1`, mémoriser `(witness, tuple(sorted(observed)))` par paire (liste : une paire peut être signalée depuis ses deux bouts) ; émettre les contrôles depuis cette mémoire. Ajouter un test de permutation sur cette variante et asserter `refs` + `details.neighbors` dans `test_two_observed_neighbors…`.

**H2 — Auto-observation d'un port = exception** — `merge.py:60-72` puis `:119-123` (`Link` → `link_endpoints_equal`).
Un document LLDP `A/p → A/p` (bouchon de boucle, réflecteur, convertisseur de média qui renvoie les trames : cas réel) produit un groupe dont les deux bouts sont égaux, refusé par le contrat. Sonde C. Le contrat d'entrée l'accepte.
Correction : dans `group()`, si `_target_key(claim) == witness`, ne pas créer de groupe et émettre un contrôle ; il n'y a pas de code pour ça → à ajouter au catalogue (`self_observation`, warning) et à `docs/05` §4, ou à trancher avec Orhan.

## MOYEN

**M1 — `details.observed` de `description_disagrees_with_observed` non déterministe** — `merge.py:96`.
`items[0].port` prend la forme brute du premier claim du groupe. Deux documents LLDP vers un stub en formes courte et longue (`Gi0/1`, `GigabitEthernet0/1`) tombent dans le même groupe par équivalence ; le détail dépend de l'ordre des documents (sonde G : octets différents). Correction : utiliser `_display_name(key, items)` ou `key[1]` (forme d'équivalence), jamais `items[0]`.

**M2 — Désaccord non détecté quand l'observation vient de l'autre bout** — `merge.py:77-93`.
`docs/05` R3 définit le désaccord par **endpoint** (« un endpoint (h, i) qui apparaît dans un claim observé vers X et dans un claim documenté vers Y ») ; le code ne compare que les claims d'un même témoin. Sonde H : `sw-core-01/Ethernet1/3` observe `fw-edge-01/x1`, la description de `x1` dit `sw-core-01|Ethernet1/5` → deux câbles sur `x1` (`confirmed` + `documented_only`), aucun `description_disagrees_with_observed`. C'est exactement le cas Fortinet (pas de LLDP, descriptions seules), donc fréquent. Correction : après `group()`, pour chaque groupe documenté seul, si l'un de ses bouts est déjà bout d'un groupe observé, supprimer le groupe et émettre le désaccord depuis le témoin documenté. À confirmer avec Orhan que c'est bien la sémantique voulue.

**M3 — MAC distante non résolue chez un device collecté : deux arêtes pour un câble** — `ifnames.py:57-61` + `merge.py`.
Si aucune interface de B ne porte la MAC (`mac_address` null, topic `interfaces` en échec), l'endpoint reste `(B, MAC)` ; la description de B sur ce port crée alors un second câble `documented_only` vers `(B, x1)` (sonde I : `Ethernet1/3` porte `fw-edge-01/70:4c:…` confirmed et `fw-edge-01/x1` documented_only). Même racine que M2 : la réconciliation « accord jugé sur le device » n'est appliquée qu'au témoin de l'observé. Correction avec M2 : un claim documenté de B vers A/p, quand A/p observe `(B, MAC)`, rejoint le groupe observé.

**M4 — Un claim documenté sans port confirme plusieurs câbles** — `merge.py:81-88`.
`matched` peut contenir plusieurs cibles du même device ; l'évidence est dupliquée dans chaque lien et une seule description « confirme » deux câbles (sonde N : `C1|sw-core-02|` confirme `Ethernet1/4` et `Ethernet1/5`). Même effet avec `any(c.port_is_mac …)` et deux cibles MAC. Correction : n'attacher que si `len(matched) == 1`, sinon désaccord (détails : les cibles) ; à écrire dans R3.

**M5 — `vendor == "cisco"` octet pour octet** — `claims.py:18`, `:66`.
`vendor` est une chaîne libre (CLAUDE.md, décision 2026-09-10) : « Cisco », « Cisco Systems ». Sonde M : le lien se forme quand même grâce à `equivalent()` dans les clés, mais `remote_resolved.interface` garde `Gi0/0/0` alors que l'endpoint affiche `GigabitEthernet0/0/0`, et `ifname_short_to_long` n'est pas compté : évidence incohérente avec le lien. Correction : règle explicite dans `docs/05` R1 (`vendor.casefold().startswith("cisco")` ou ensemble fermé) et test.

**M6 — IPv6 annoncée sous une autre forme que celle stockée** — `identity.py:44-45`, `context.py:103`.
`by_ip.get(raw)` est textuel : `2001:DB8::1` annoncé contre `2001:db8::1` en `ip_addresses` → stub `2001:db8::1` + `neighbor_unknown` au lieu de `address` (sonde J). Correction : normaliser les deux côtés par `str(ipaddress.ip_address(...))`.

**M7 — Repli sur `interfaces[].members` conditionné au mauvais critère** — `context.py:70`, `:79`.
`docs/05` R4/§2.2 : repli « si le topic `aggregates` est absent pour ce device ». Le code teste « le device a au moins un document d'agrégat ». Topic en `success` sans port-channel → repli avec `member_status=None` (sonde O). Correction : construire `coverage` d'abord et tester `topics.aggregates == ABSENT`.
